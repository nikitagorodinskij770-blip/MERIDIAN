## 1. Границы системы

MERIDIAN состоит из трёх процессов и одного файла базы данных.

```
┌─────────────────────────────────────────────────────────────┐
│  Браузер                                                    │
│  ┌───────────────┐  ┌──────────────┐  ┌─────────────────┐   │
│  │ Роутер + вью  │  │ Движок рынка │  │ Слой сессии     │   │
│  └───────┬───────┘  └──────┬───────┘  └────────┬────────┘   │
└──────────┼─────────────────┼───────────────────┼────────────┘
           │ REST /v1        │ WSS + REST        │ REST /v1
           ▼                 ▼                   ▼
┌──────────────────┐  ┌──────────────┐  ┌──────────────────┐
│ server/app.py    │  │ Биржи:       │  │ server/app.py    │
│ (HTTP + статика) │  │ Binance, OKX,│  │ (аутентификация) │
└────────┬─────────┘  │ Bybit, …     │  └────────┬─────────┘
         │            └──────────────┘           │
         ▼                                       ▼
┌─────────────────────────────────────────────────────────────┐
│  SQLite (WAL): meridian.db                                  │
│  29 таблиц · 6 представлений · триггеры целостности         │
└─────────────────────────────────────────────────────────────┘
```

**Почему один процесс отдаёт и API, и статику.** Разделение потребовало бы
согласовывать CSP в двух местах, настраивать CORS между своими же компонентами
и держать вторую конфигурацию. Для текущего масштаба это чистые накладные
расходы. При росте нагрузки статика уходит на CDN — код к этому готов, потому
что фронтенд не знает о сервере ничего, кроме префикса `/v1`.

**Почему SQLite, а не PostgreSQL.** На целевой машине нет ни Node, ни pip-пакетов.
SQLite входит в стандартную библиотеку Python, поддерживает WAL (чтение не
блокирует запись), внешние ключи, триггеры, частичные индексы и оконные функции.
Схема написана на подмножестве SQL, переносимом на PostgreSQL: замена сводится
к строке подключения и типу `INTEGER PRIMARY KEY AUTOINCREMENT` → `BIGSERIAL`.
Ограничение SQLite — один писатель одновременно; при обороте выше нескольких
сотен операций в секунду потребуется миграция.

## 2. Слои и зависимости

```
server/
  schema.sql      DDL основного контура
  schema_v2.sql   DDL кабинетов, поддержки, персонала
  db.py           подключение, справочники, post_tx()  ← не зависит ни от чего
  security.py     пароли, сессии, подпись             ← зависит от db
  accounts.py     кабинеты, поддержка, персонал        ← зависит от db, security
  engine.py       матчинг, депозиты, выводы            ← зависит от db
  routes_v2.py    маршруты кабинетов и админки         ← зависит от всех
  app.py          HTTP-транспорт                       ← зависит от всех
  selftest.py     26 проверок инвариантов
```

Зависимости направлены строго вверх: `db.py` не импортирует ничего из проекта,
поэтому его можно тестировать изолированно. Единственное исключение —
`security.create_session()` импортирует `accounts` внутри функции, а не на
уровне модуля: это разрывает цикл, который иначе возник бы из-за того, что
`accounts` нужны хэши паролей.

## 3. Модель данных

### 3.1 Справочники

| Таблица | Назначение | Ключевые ограничения |
|---|---|---|
| `assets` | активы и их точность | `scale` 0–18, определяет минимальную единицу |
| `networks` | блокчейн-сети | `addr_format` задаёт правила валидации адреса |
| `asset_networks` | какой актив в какой сети ходит | комиссии и минимумы в минорных единицах |
| `markets` | торговые пары | `base_id <> quote_id` |
| `asset_prices` | последние котировки в USD | заполняется фронтендом, читается сервером |

### 3.2 Учётные записи

| Таблица | Назначение |
|---|---|
| `users` | учётные записи; `CHECK` требует основание при блокировке |
| `sessions` | активные сессии с гео и устройством; хранится хэш токена |
| `login_history` | журнал входов навсегда — переживает удаление сессии |
| `known_devices` | отпечатки устройств для распознавания нового входа |
| `api_keys` | ключи с правами; секрет зашифрован на ключе экземпляра |
| `request_nonces` | одноразовые метки запросов против повторов |
| `staff_profiles` | должность, отдел и точный набор полномочий |
| `user_limits` | персональные лимиты, переопределяют общие |
| `user_notes` | внутренние заметки операторов |

### 3.3 Деньги

| Таблица | Назначение |
|---|---|
| `ledger_accounts` | план счетов: клиентские, заблокированные, комиссии, казначейство |
| `ledger_tx` | шапка операции: одно бизнес-событие |
| `ledger_entries` | проводки; дебет положителен, кредит отрицателен |
| `balances` | материализованный остаток, обновляется триггером |
| `orders`, `fills` | заявки и исполнения |
| `transactions` | ввод и вывод средств |

### 3.4 Взаимодействие

| Таблица | Назначение |
|---|---|
| `notifications` | персональные уведомления |
| `support_tickets` | обращения; триггер обновляет статус при новом сообщении |
| `support_messages` | переписка; `is_internal` скрывает заметки от клиента |
| `audit_log` | журнал действий, только на добавление |

### 3.5 Представления

* `v_user_balances` — доступный и заблокированный остаток по клиенту.
* `v_ledger_imbalance` — **должно быть пустым**. Непустой результат означает
  повреждение журнала и требует остановки операций.
* `v_user_summary` — сводка кабинета: счётчики операций, входов, устройств.
* `v_staff_activity` — нагрузка на операторов поддержки.
* `v_support_queue` — очередь обращений с возрастом и приоритетом.
* `v_open_orders` — открытая часть книги заявок.

## 4. Денежный контур

### 4.1 Целые числа вместо дробных

Каждая сумма хранится в минимальных единицах актива. Для BTC при `scale = 8`
величина 0.5 BTC хранится как `50000000`.

Причина прямая: `0.1 + 0.2 !== 0.3` в двоичной плавающей точке. Биржа, которая
складывает балансы во `float`, теряет доли минимальной единицы на каждой
операции. Через миллион сделок расхождение становится заметным, а свести баланс
уже невозможно — потому что неизвестно, где именно потерялось.

Преобразование выполняют `db.to_minor()` и `db.to_human()`. Оба работают через
`Decimal`, а не через умножение `float` на степень десяти:

```python
from decimal import Decimal, ROUND_DOWN
factor = Decimal(10) ** scale
minor = int((Decimal(str(human)) * factor).quantize(Decimal(1), rounding=ROUND_DOWN))
```

`ROUND_DOWN` выбран намеренно: округление в пользу площадки, а не клиента,
исключает создание средств из ничего при конвертации.

Обратное преобразование использует `format(value, "f")`. Без этого `Decimal`
нормализует 50000 в `5E+4` — научная запись в финансовом API ломает разбор
на стороне клиента. Этот дефект был обнаружен сквозным тестом и исправлен.

### 4.2 Двойная запись

Баланс — не поле, которое обновляют, а следствие журнала проводок.

```
Клиент пополняет 1000 USDT:

  ledger_tx: { kind: 'deposit', memo: 'пополнение USDT через TRC20' }
  ledger_entries:
    external(USDT)      −1000000000     ← средства пришли извне
    user:alice(USDT)    +1000000000     ← и попали на счёт клиента
                        ───────────
                        сумма = 0       ← инвариант
```

`db.post_tx()` — единственный способ изменить баланс. Он проверяет сумму по
каждому активу **до** записи и отклоняет несбалансированную операцию, вместо
того чтобы «чинить» её потом.

`balances` — лишь кэш, поддерживаемый триггером `trg_entry_balance`. Он нужен,
чтобы не пересчитывать сумму по всему журналу на каждый запрос. Расхождение
кэша с журналом обнаруживает `db.check_integrity()`, доступный по
`GET /v1/health` и `GET /v1/admin/integrity`.

### 4.3 Запрет отрицательного остатка

Триггер `trg_no_negative_user_balance` прерывает транзакцию при попытке увести
клиентский счёт в минус:

```sql
CREATE TRIGGER trg_no_negative_user_balance
AFTER UPDATE ON balances
WHEN NEW.amount < 0
 AND (SELECT kind FROM ledger_accounts WHERE id = NEW.account_id) IN ('user','locked')
BEGIN
    SELECT RAISE(ABORT, 'INSUFFICIENT_BALANCE');
END;
```

Проверка на уровне базы, а не приложения — принципиальна. Прикладной код можно
обойти новым эндпоинтом, забытой веткой или ошибкой в условии; триггер
срабатывает всегда, независимо от того, кто и как пишет в таблицу.

Системные счета (`external`, `hot_wallet`, `treasury`) уходить в минус могут:
для них отрицательный остаток осмыслен и означает обязательство.

## 5. Матчинг-движок

### 5.1 Приоритет «цена — время»

Среди заявок с одинаковой ценой первой исполняется поданная раньше.

```python
rows = SELECT * FROM orders
       WHERE market=? AND side=<противоположная> AND status IN ('open','partially_filled')
         AND user_id <> ?                       -- запрет самосделок
         AND (price <= ? для покупки | price >= ? для продажи)
       ORDER BY price ASC|DESC, created_at ASC  -- цена, затем время
```

Сортировка по `created_at ASC` внутри уровня цены и есть временной приоритет.
Он защищает от переупорядочивания заявок в пользу отдельных участников.

### 5.2 Цена сделки — цена мейкера

Исполнение проходит по цене той заявки, которая уже стояла в книге. Это
стандарт, и он же защищает от манипуляции: агрессивная заявка не может
получить цену лучше выставленной.

### 5.3 Резервирование средств

Средства блокируются до размещения заявки переводом на счёт `locked`:

```
Покупка 1 BTC по 60000 USDT:
  user:alice(USDT)   −60000000000
  locked:alice(USDT) +60000000000
```

Заблокированное нельзя потратить — тот же триггер не даст увести `locked`
в минус. При отмене заявки резерв возвращается обратной проводкой.

Для рыночной заявки на покупку резерв считается по худшей цене в книге:
иначе неизвестно, сколько потребуется. Излишек возвращается после исполнения.

### 5.4 Идемпотентность

`clientOrderId` защищён частичным уникальным индексом:

```sql
CREATE UNIQUE INDEX idx_orders_client_ref
    ON orders(user_id, client_ref) WHERE client_ref IS NOT NULL;
```

Повторный запрос с тем же идентификатором вернёт существующую заявку, а не
создаст вторую. Это важно при обрыве связи: клиент не знает, дошёл ли запрос,
и повторяет его.

Депозиты идемпотентны по паре «сеть + хэш транзакции»: тот же блокчейн-перевод
не зачислится дважды.

## 6. Аутентификация и сессии

### 6.1 Пароли

scrypt с параметрами N=2¹⁵, r=8, p=1, длина ключа 32 байта.

scrypt, а не «просто SHA-256»: он требует памяти, что делает перебор на GPU
несоизмеримо дороже. При N=2¹⁵ и r=8 требуется 32 МиБ на попытку — видеокарта
с тысячами ядер не может запустить тысячи параллельных проверок.

Формат хранения: `scrypt$N$r$p$salt_b64$hash_b64` — параметры записаны рядом
с хэшем, поэтому их можно поднять без миграции старых записей.

Сравнение через `hmac.compare_digest()`: обычное `==` прекращает сравнение
на первом различии, и по времени ответа восстанавливается хэш побайтово.

**Замеченная особенность.** OpenSSL по умолчанию ограничивает scrypt 32 МиБ,
а N=2¹⁵, r=8 требует ровно столько плюс служебные структуры — вызов падал
с `memory limit exceeded`. Решение: явно передавать `maxmem`, а не ослаблять
параметры до заведомо слабых.

### 6.2 Сессии

В базе хранится SHA-256 от токена, не сам токен. Утечка дампа базы не даёт
войти под чужой учётной записью.

На клиенте токен лежит в `sessionStorage`, а не в `localStorage`: он умирает
вместе с вкладкой, что сокращает окно для кражи через XSS и не оставляет
доступ на общем компьютере.

Смена пароля отзывает все сессии, кроме текущей. Без этого смена пароля после
компрометации была бы бессмысленной — злоумышленник остался бы внутри.

### 6.3 Журнал входов и устройства

`login_history` отделён от `sessions` намеренно: сессия истекает и удаляется,
а история входов нужна навсегда — это основной инструмент расследования,
когда клиент заявляет о несанкционированном доступе.

Отпечаток устройства — SHA-256 от типа, ОС и браузера. Это не идентификация
личности, а способ отличить привычный вход от нового. При входе с неизвестного
отпечатка создаётся уведомление уровня `warning`.

Геолокация по IP выполняется **локально**: обращение к внешнему сервису
отправило бы IP клиента третьей стороне без его согласия. Определяются
частные диапазоны; при подключении собственной базы GeoIP правится одна
функция `accounts.geo_lookup()`.

## 7. Подпись запросов

### 7.1 Канонизация

```
METHOD \n PATH \n TIMESTAMP \n NONCE \n SHA256(body)
```

Строка одинакова на сервере (`security.canonical_string`) и на клиенте
(`js/api/sign.js`). Любое расхождение — вплоть до порядка полей — ломает
подпись, поэтому обе реализации меняются только вместе.

### 7.2 Три преграды повтору

| Преграда | Что закрывает |
|---|---|
| Окно ±30 с | перехваченный запрос устаревает |
| Одноразовый `nonce` | повтор в пределах окна отклоняется базой |
| Тело в подписи | подмена payload при сохранении подписи |

`nonce` вставляется с `PRIMARY KEY`, поэтому повтор отклоняется самой базой,
а не проверкой в коде — состязание двух параллельных запросов невозможно.

### 7.3 Хранение секрета

Проверка HMAC требует самого секрета, поэтому «хранить только хэш» не работает.
Компромисс: секрет шифруется на ключе экземпляра (`.instance_secret`, отдельный
файл вне базы) потоковым шифром на HMAC-SHA256 с тегом целостности.

Утечка одного лишь дампа базы ключи не раскрывает — нужен ещё файл секрета.
В продакшене это место занимает KMS или HSM.

### 7.4 WebCrypto на клиенте

Секрет импортируется в `CryptoKey` с `extractable: false`. Скомпрометированный
код страницы сможет попросить подпись, но не сможет извлечь сам секрет.

Совместимость проверена сквозным сценарием: браузер подписывает через
WebCrypto, Python принимает; подделка секрета даёт `BAD_SIGNATURE`, повтор
`nonce` — `NONCE_REUSED`.

## 8. Рыночные данные

### 8.1 Источники

| Источник | Что даёт | Транспорт |
|---|---|---|
| Binance | 23 криптоактива, свечи, стакан, лента | WebSocket + REST |
| Coinbase | 10 фиатных валют, TON, DAI, курс USDT | REST |
| CoinGecko | активы вне первых двух | REST |
| OKX, Bybit, Kraken, Bitstamp | сводная цена оракула | REST |

Все опрошенные площадки отдают CORS-заголовки браузеру — это проверено, а не
предположено. Ключи доступа не используются, сведения о пользователе никуда
не передаются.

### 8.2 Прайс-оракул

Цена одной биржи — не истина. Сломанный стакан или тонкая ликвидность дают
выброс, который сдвинет среднее. Поэтому:

1. Параллельный опрос шести площадок, каждая через свой ограничитель частоты.
2. Медиана цен — устойчива к одному сломавшемуся источнику.
3. Отбраковка по MAD (медианное абсолютное отклонение): всё дальше 3·MAD
   отбрасывается. MAD выбран вместо сигмы, потому что сам выброс раздувает
   сигму и тем самым маскирует себя.
4. Порог не ниже 0.25% — иначе при полном согласии площадок отсеклись бы
   нормальные расхождения.
5. По выжившим — медиана, взвешенная по суточному обороту: вес голоса
   площадки равен её ликвидности.

Измеренный разброс между шестью биржами: около 0.09% по BTC.

### 8.3 Ограничитель частоты

Портирован по образцу `RateLimitGate` из CryptoExchange.Net: скользящее окно
плюс отдельный guard на `Retry-After`.

Без ограничителя быстрое переключение пар в терминале выстреливает пачкой
запросов, приводит к 429, а затем к временному бану IP. Запросы выстраиваются
в последовательную цепочку, поэтому лимит не обходится состязанием.

### 8.4 Направление потока котировок

Котировки идут **от браузера к серверу**, а не наоборот.

У фронтенда уже есть живой WebSocket-поток. Дублировать исходящие соединения
с бэкенда означало бы удвоить нагрузку на биржи и добавить точку отказа.
Сервер хранит последнее известное значение в `asset_prices` и использует его
для оценки портфеля и отчётов — так эти экраны не зависят от доступности
биржи в момент запроса.

## 9. Личные кабинеты

### 9.1 Состав

| Раздел | Содержание |

### 9.2 Один запрос вместо пяти

`GET /v1/me/overview` возвращает всё для главного экрана: профиль, балансы,
оценку портфеля, счётчики, лимиты и число непрочитанных уведомлений.

Пять параллельных запросов с фронта дали бы пятикратные накладные расходы
и мерцающий интерфейс, где блоки появляются вразнобой.

### 9.3 Статистика

`accounts.user_activity()` строит ряды по дням. Суммы приводятся к USD по
курсам из `asset_prices` — складывать BTC с рублями бессмысленно.

Курс берётся из базы, а не с биржи: серверу незачем открывать исходящее
соединение ради экрана статистики.

## 10. Административный контур

### 10.1 Модель полномочий

Роль в `users.role` даёт базовый доступ, `staff_profiles.permissions` — точный
набор. Два оператора поддержки при одной роли могут иметь разные полномочия.

```
users.role = 'support'  → доступ к разделу
permissions = 'users.view,support.reply,notify.send'  → что именно можно
```

**Новый сотрудник по умолчанию не может ничего.** Права выдаются явно.
Единственное исключение — корневой администратор: учётная запись с ролью
`admin` без профиля сотрудника. Такая заводится при развёртывании, когда
выдавать ей права ещё некому.

Полный список — 12 полномочий, от `users.view` до `platform.settings`.
Типовые наборы по отделам подставляются при выборе отдела и уточняются вручную.

### 10.2 Функции панели

| # | Функция | Требуемое право |
|---|---|---|
| 1 | Поиск клиентов с фильтрами | `users.view` |

| 3 | Блокировка и разблокировка с основанием | `users.block` |
| 4 | Изменение уровня верификации | `users.kyc` |

| 7 | Принудительное завершение сессий | `users.sessions` |

### 10.3 Обязательное основание

Блокировка, сброс 2FA и корректировка баланса требуют текстового основания.
Оно попадает в `audit_log` и доступно при проверке.

Для блокировки требование продублировано на уровне схемы:

```sql
CHECK (status <> 'blocked' OR (block_reason IS NOT NULL AND length(block_reason) > 0))
```

Блокировка без причины невозможна физически, а не только по договорённости.

### 10.4 Корректировка баланса

Проводится двойной записью через казначейский счёт. Знак суммы определяет
направление. Операция отражается в журнале как `adjustment` с основанием,
и клиент получает уведомление — скрытая правка баланса невозможна.

## 11. Клиентская архитектура

### 11.1 Без сборки

Чистые ES-модули, загружаемые браузером напрямую. Ни webpack, ни npm.

Причина исходная — отсутствие Node на машине. Следствия оказались полезными:
нулевое время сборки, отсутствие цепочки зависимостей с её уязвимостями,
и возможность открыть любой файл и увидеть исполняемый код без карт исходников.

### 11.2 Жизненный цикл вью

```javascript
export default {
  title: 'Заголовок вкладки',
  auth: true,                     // требуется вход
  render({ params }) {
    const el = h(`<div>…</div>`);
    el._mounted = () => { … };    // после вставки в DOM
    el._cleanup = () => { … };    // при уходе со страницы
    return el;
  },
};
```

`_mounted` необходим потому, что вью строится до вставки в документ — у
элементов ещё нет размеров, и `canvas` при отрисовке получил бы нулевую
геометрию. Хук вызывается роутером уже после `appendChild`.

`_cleanup` снимает подписки и таймеры. Без него переход между страницами
оставлял бы работающие интервалы.

### 11.3 Графики

Написаны вручную на `<canvas>`: свечи, область, столбцы, спарклайны, донат,
глубина рынка. Внешняя библиотека потребовала бы либо CDN (запрещён нашей CSP),
либо вендоринга сотен килобайт ради четырёх типов графиков.

Все функции отрисовки защищены `ensureSized()`: если элемент ещё не получил
размер, подписка на `ResizeObserver` плюс несколько отложенных попыток
гарантируют отрисовку, когда геометрия появится. Избыточность намеренна —
`ResizeObserver` молчит, если элемент вставлен уже с готовым размером.

### 11.4 Фоновая среда

Фон живёт в `position: fixed` слое под контентом, поэтому не кончается вместе
со страницей и не прокручивается вместе с ней. Пять слоёв: градиент, сетка,
свечение с медленным дрейфом, виньетка, зерно.

## 12. Безопасность

### 12.1 Content Security Policy

```
default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';
connect-src 'self' <закрытый список бирж>;
frame-ancestors 'none'; object-src 'none'; base-uri 'self'
```

Задаётся и заголовком сервера, и `<meta>` в разметке — второе покрывает случай
статического размещения без нашего сервера.

`connect-src` — закрытый список: внедрённый скрипт не сможет отправить данные
никуда, кроме перечисленных бирж. Проверено: посторонний домен, инлайновый
скрипт и внешний скрипт блокируются, разрешённые биржи проходят.

### 12.2 Проверка адресов

Опечатка в адресе означает безвозвратную потерю средств, и единственный момент,
когда её можно поймать, — до отправки.

* **EIP-55** для EVM-сетей: регистр букв кодирует keccak-256 адреса.
* **Base58Check** для Bitcoin и TRON: двойной SHA-256.
* **Bech32/Bech32m** для `bc1…`: полином над GF(32).

keccak-256 реализован вручную: **в WebCrypto его нет**. Там семейства SHA-2
и SHA-3, а Ethereum использует оригинальный Keccak с другим дополнением
(`0x01` вместо `0x06`) — подмена на SHA3-256 даёт неверный результат.

Проверено по официальным векторам: `keccak256("")` и `keccak256("abc")`
совпали побайтово, все четыре адреса из текста EIP-55 прошли, опечатка
в одном символе регистра поймана.

### 12.3 Защита от подмены домена

Приложение знает свой легитимный домен и заявляет о подмене само. Ловит
клоны вида `meridian-exchange.com` и омографы с кириллическими буквами.

Полоса предупреждения неубираемая: на фишинговом сайте кнопка «скрыть»
играла бы на стороне атакующего.

### 12.4 Ограничение частоты

| Действие | Лимит |
|---|---|
| Регистрация | 5 в час с адреса |
| Вход | 10 за 5 минут с адреса |
| Создание обращения | 5 в час с учётной записи |

Ответ на неизвестный адрес и на неверный пароль одинаков — иначе форма входа
превращается в инструмент проверки существования учётных записей.

## 13. Отказоустойчивость

| Отказ | Поведение |
|---|---|
| Биржа не отвечает | актив переходит на расчётную котировку, интерфейс работает |
| WebSocket оборвался | переподключение с возрастающей паузой, до 6 попыток |
| Бэкенд недоступен | публичные разделы работают, кабинет показывает состояние |
| Некорректный UTF-8 в теле | ответ 400, соединение живо |
| Тело больше 1 МБ | ответ 413 до чтения |
| Несбалансированная проводка | отклонена до записи |
| Попытка увести счёт в минус | прервана триггером базы |

**Замеченный дефект.** Некорректный UTF-8 в теле запроса ронял соединение
с необработанным `UnicodeDecodeError`. Исправлено: тело читается целиком даже
когда оно негодное — иначе непрочитанные байты остались бы в сокете и «съехали»
на следующий запрос в keep-alive.

## 14. Что реализовано, а что нет

### Реализовано и проверено

* Схема БД с ограничениями, триггерами и представлениями целостности.
* Двойная запись; 26 автоматических проверок инвариантов.
* Матчинг «цена — время» с резервированием и идемпотентностью.
* scrypt-пароли, сессии, подпись HMAC-SHA256, защита от повторов.
* Личные кабинеты: устройства, гео, история входов, статистика.
* Поддержка: обращения, переписка, внутренние заметки.
* Уведомления с уровнями важности.
* Административный контур: 17 функций с разграничением полномочий.
* CSP, EIP-55, Base58Check, Bech32, защита от подмены домена.
* Агрегация котировок шести бирж с отбраковкой выбросов.

### Не реализовано

| Компонент | Текущее состояние | Что требуется |
|---|---|---|
| Деривация депозит-адресов | случайная строка нужного формата | HD-вывод из xpub, BIP-32/44 |
| Зачисление депозитов | вызывается явно | воркер, читающий блокчейн |
| Исполнение выводов | заявка меняет статус | подпись транзакции в кастоди |
| Двухфакторная защита | поле есть, проверки нет | TOTP по RFC 6238 |
| Рассылки | статус меняется | интеграция с почтовым провайдером |
| Геолокация по IP | частные диапазоны | база GeoIP локально |
| KYC-верификация | уровень меняется вручную | внешний провайдер с вебхуком |

Все места отмечены в коде. Ни одно из них не влияет на корректность денежного
контура: он замкнут и проверяем независимо от того, откуда пришли средства.
